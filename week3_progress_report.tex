\section*{A. Proposed Approach}
Our approach relies on a modular monolith architecture. This balances development velocity with strong isolation, avoiding the overhead of managing distributed microservices. We chose Keycloak (v26.8.0) as our Identity Provider to handle authentication, OIDC flows, and token lifecycles. Building a custom IdP is risky, and Keycloak provides industry-standard security out of the box.

For authorization, we use Casbin as our policy engine. While Keycloak has built-in authorization, it proved too rigid for our dynamic, tenant-specific, and relationship-based rules (like "instructors can only grade their assigned courses"). Casbin lets us define clear Role-Based Access Control (RBAC) rules, while our application database (PostgreSQL v16.15) acts as the source of truth for dynamic relationships and active tenant memberships.

\section*{B. System Design}
The system architecture includes the following major components, all deployed via Docker Compose for reproducibility:
\begin{itemize}
    \item \textbf{Clients:} Lightweight web and mobile-style browser interfaces. They use Authorization Code Flow with PKCE. The clients never handle user passwords directly.
    \item \textbf{Identity Provider (Keycloak):} Manages credentials, enterprise federation (OIDC brokering), and issues JSON Web Tokens (JWTs).
    \item \textbf{Backend API (Fastify):} A Node.js backend that validates JWT signatures, enforces uncached introspection, and maps the provider subject to our internal users.
    \item \textbf{Database (PostgreSQL):} Stores application state including organizations, memberships, learning resources, and audit logs. It enforces strict data integrity using unique constraints, quotas, and composite foreign keys to prevent cross-tenant data leaks.
\end{itemize}

\textbf{Workflow:} When a user accesses the platform, they authenticate via Keycloak and receive an access token. The client sends this token along with an \texttt{X-Organization-ID} header to our API. The backend strictly validates the token and checks if the user has an active membership in the requested tenant. Casbin then evaluates the user's role against the requested resource. The API executes the action and commits an audit log within the same database transaction.

\section*{C. Technical Feasibility}

    \item Node.js (v24.21.0), Fastify (v5.12.5)
    \item PostgreSQL (v16.15) with Kysely for migrations
    \item Keycloak (v26.8.0)
    \item Casbin (v5.51.1)
    \item Docker and Docker Compose
    \item Vitest and Playwright for security and browser testing
\end{itemize}

\textbf{Challenges and Mitigation:} One of the major challenges we addressed this week was ensuring the safety of our introspection logic. We added strict environment validation so that introspection cannot be accidentally disabled in production (failing closed). We also verified that local PostgreSQL transactions handle application provisioning atomically, keeping it isolated from any external IdP modifications. Another insight was that a password reset does not automatically revoke existing Keycloak access sessions, so we documented that incident response must include an explicit \texttt{logout-all}.
