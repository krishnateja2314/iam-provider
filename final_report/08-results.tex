\subsection{Session revocation latency}

These are local samples on one machine, not a service-level guarantee. The AG02 value is the fastest because revocation is a single database update that the next request reads directly; the others include a remote call to Keycloak.

\paragraph{Live provider observations, repeated in every run.} Password reset: old password rejected, new password accepted, already-issued access token still \textbf{200}, so a reset alone does not revoke sessions and incident response must call \code{logout-all}. Refresh replay: replayed refresh token 400, its successor refresh token 400, and the successor access token 401, so replaying an old refresh token kills the whole token family.

\subsection{Latency observation}
\label{sec:latency}
Because every request is introspected without a cache, we measure what that costs. \code{scripts/measure-latency.mjs} runs inside the backend container (to exclude Docker Desktop's port forwarding, issue 30) and sends 3 runs of 200 sequential requests per series after a warm-up.

\begin{table}[H]
\centering
\small
\begin{tabular}{@{}lcc@{}}

Introspection call alone & 4.04 / 3.29 / 2.73 & 7.14 / 5.56 / 5.58\\

The provider check is roughly a third of an authenticated agent request (median p50 3.3 of 9.3\,ms). This is the price of rejecting a revoked credential on the next request. It is a sequential, single-machine observation, not a benchmark.

\subsection{Real-browser proof}
The Playwright proof drove Microsoft Edge against the clean stack and passed all 11 checks:
\begin{enumerate}
  \item the provider's bounded admin service account cannot change realm settings (403);
  \item a wrong PKCE verifier is rejected by the provider (400);
  \item web login with S256 PKCE and signed audience, type, role and subject checks;
  \item the tenant selector: the same user is admin in one tenant and learner in the other; published lists; members 403; a cross-tenant resource ID 404; tenant-scoped allow and deny audit;
  \item \textbf{new:} an AG02 delegation created by clicking the button, then used by the real agent: 200 in scope, 403 on members and in the other tenant, 401 after revocation;
  \item mobile-client login with PKCE;
  \item enterprise broker login on the web client;
  \item enterprise broker login on the mobile client;
  \item own-session listing excludes other users, and deleting another user's real session is refused;
  \item refresh rotation, and the old refresh token is rejected on replay;
  \item revoking one session rejects its access and refresh tokens immediately while another device stays signed in.
\end{enumerate}
We then restarted the same stack with \code{IAM\_PUBLIC\_HOST=127.0.0.1}, so that the provider's issuer, the API's expected issuer, CORS and the clients' runtime configuration all changed, ran the Keycloak updater, and repeated the proof: \textbf{11 of 11 PASS} with no source change. Under that issuer the AG02 demo script gave: no delegation 403; with Charlie's delegation, resources 200 (3 rows) and submissions 200 (his 2 rows only); members 403; the same delegation in Globex 403.

\subsection{Physical phone (Week~5)}
On 7 November (code identical to \texttt{fde2efd}), a realme 11 Pro+ (Android~15, Chrome~156) connected through the phone's own hotspot ran the mobile client against the laptop: Alice signed in with PKCE and saw Acme resources and members (200), Globex resources (200) and \textbf{Globex members 403}; session listing, refresh rotation and sign-out worked; the enterprise user signed in through the broker and was refused Acme members (403). The run is on video, with checksums in \code{docs/evidence/2026-11-07/phone-run.md}; frames are shown in Figures~\ref{fig:phone} and~\ref{fig:phone-setup}. It needed Chrome's secure-origin flag (issue 31). The phone run was not repeated for the AG02 change, which adds two buttons and no change to the login flow.
